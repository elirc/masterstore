# Concepts: parsing, query identity, and boundaries

A URL filter is data supplied by a caller. Parsing it is different from trusting it. `Number.parseInt` is permissive: it reads an initial numeric prefix and ignores a suffix. That is convenient for informal text but wrong for a contract where `price_min` should be one whole number. The fix uses a digit-only check and then a safe-integer check. It accepts `0`, `12`, and `0012` (normalized to `12`); it rejects signs, decimals, suffixes, surrounding spaces, empty strings, exponent and hex notation, and values that cannot be represented exactly.

This is the *read* part of CRUD: the server parses query state and uses it to retrieve a product collection. Parsing a filter does not create or update anything. Query identity is the full normalized filter set — `listingKey` (`listing-search-params.ts:156-165`) makes that identity concrete as a JSON string — so the same accepted parameters always produce the same request and the same cache entry. That is different from *request* idempotency: parsing the same URL twice is trivially stable, while webhook idempotency asks whether repeating an event repeats an external effect such as an email. The repository's webhook guard (`lib/webhooks/handlers.ts:28`) is an in-memory `Set`; this change does not touch it.

The parser also has limits on what it can promise. It can drop malformed filters, but it cannot authorize a customer, prove a price range is sensible (`price_min=500&price_max=10` passes straight through to `price_gte: 500, price_lte: 10`), or make a ten-minute-cached catalog response fresh. Those belong to the route, the query builder, and Spree.

**Silent omission is a policy, not an accident.** The module already treats an unknown `availability` value as absent (`listing-search-params.ts:73-77`), so dropping a malformed price bound follows the existing convention. Note the inconsistency it leaves: `sort` has no allowlist at all and any trimmed string is forwarded to Spree (see F1 in [06](06-SOLUTIONS-AND-REVIEW.md)). If a future requirement needs a visible validation error, that is a new contract with tests at the route boundary.
