# Concepts: parsing, query identity, and boundaries

A URL filter is data supplied by a caller. Parsing it is different from trusting it. `Number.parseInt` is permissive: it reads an initial numeric prefix and ignores a suffix. That is convenient for informal text but unsafe for a contract where `price_min` should be one whole number. The fix uses a digit-only predicate and then checks safe integer range. It accepts `0`, `12`, and digit strings such as `0012`; it rejects signs, decimals, suffixes, empty strings, and values that cannot be represented exactly.

CRUD thinking helps here. This is the read part of CRUD: the server parses query state and uses it to retrieve a product collection. Parsing a filter does not create or update a product. Query identity is determined by the full normalized filter set, so the same accepted parameters should produce the same request. This is separate from request idempotency: parsing the same URL twice should be stable, while webhook idempotency asks whether repeating an event should repeat an external effect. The repository's webhook `Set` is in-memory and deployment-limited; this change does not pretend to make it durable.

The data boundary also has authorization and failure limits. A strict parser can remove malformed filters, but it cannot authorize a customer, prove a price is allowed, or make a catalog response fresh. Those responsibilities belong to route, service, and provider layers. In review, ask whether silently dropping a bad filter is the desired product policy; this project already treats invalid availability as absent, so the change follows that convention. If a future requirement needs a visible validation error, that is a new API contract requiring tests at the route boundary.
